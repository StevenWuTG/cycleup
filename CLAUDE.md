# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CycleUp — a marketplace for upcycled/repurposed goods, connecting independent makers with eco-conscious buyers. React frontend backed directly by Supabase (Postgres + Auth + Storage); there is no custom server.

## Commands

- `npm run dev` — start the Vite dev server (HMR)
- `npm run build` — production build
- `npm run preview` — preview the production build locally
- `npm run lint` — run ESLint

No test suite is configured. To test anything that needs two signed-in users (messaging), run a second dev server on another port (`npm run dev -- --port 5174`): Supabase sessions live in `localStorage`, which is per-origin, so each port keeps its own login. Don't use `127.0.0.1` for this — Vite binds only to IPv6 `localhost`, so `127.0.0.1` refuses connections. Test rows can't be cleaned up from the client (conversations/messages have no delete policy); remove them in the SQL Editor, e.g. `delete from public.conversations where listing_title like 'TEST%';` (messages cascade).

## Setup

Copy `.env.example` to `.env.local` and fill in `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (Supabase dashboard → Project Settings → API). `.env.local` is gitignored (`.env*` is ignored except `.env.example`); never commit real keys, and never put the `service_role` key in this frontend. Vite reads env at startup, so restart the dev server after changing it. The database is created by running [supabase/schema.sql](supabase/schema.sql) then [supabase/seed.sql](supabase/seed.sql), then [supabase/accounts.sql](supabase/accounts.sql), then [supabase/editing.sql](supabase/editing.sql), then [supabase/messaging.sql](supabase/messaging.sql), then [supabase/locations.sql](supabase/locations.sql), then [supabase/deletion.sql](supabase/deletion.sql), then [supabase/photos.sql](supabase/photos.sql) in the Supabase SQL Editor (in that order; all but the first two are re-runnable) — there is no migration tooling. Auth is Supabase email + password. In the dashboard (Authentication), "Confirm email" can be turned off for local dev; if it's on, the confirmation link redirects to the project's Site URL, which must be set to the dev URL (`http://localhost:5173`).

## Deployment

The app is a static build (`npm run build` → `dist/`) plus the hosted Supabase backend, so any static host works; it's set up for Netlify (Cloudflare Pages reads the same files). The host must define `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` as build-time environment variables (Vite inlines them at build; only these two public values are embedded — never the `service_role` key). `.node-version` pins Node 22 (Vite 8 needs ≥ 20.19 / ≥ 22.12). [public/_redirects](public/_redirects) is the SPA fallback (without it, refreshing on `/item/5` 404s). [public/_headers](public/_headers) sets security headers including a strict Content-Security-Policy: scripts only from the site itself, `connect-src`/`img-src` limited to this project's Supabase host (REST, realtime WebSocket, storage images) — the committed `public/_headers` says `*.supabase.co`, and the `scopeCspToSupabase` plugin in [vite.config.js](vite.config.js) rewrites `dist/_headers` at build time to the exact host from `VITE_SUPABASE_URL`, so the project URL is never committed (if that variable is missing at build it warns and leaves the wildcard) plus `geocoding-api.open-meteo.com`, styles/fonts from Google Fonts. **Adding any new external service (a different geocoder, analytics, an image CDN, embeds) requires updating that CSP or the browser will silently block it.** To check the real production headers locally, build and serve `dist/` with a server that applies `_headers` and the `_redirects` fallback (plain `vite preview` does neither). After deploying, Supabase → Authentication → URL Configuration must list the production URL as the Site URL (and any extra redirect URLs), or email links (confirmation, password reset) point at the wrong place.

## Architecture

- **Stack**: React 19 + Vite + React Router v7 (client-side routing, `BrowserRouter`) + Tailwind CSS v4 (via `@tailwindcss/vite`, no `tailwind.config.js` — v4 is CSS-first) + `lucide-react` for icons.
- **Routing** lives in [src/App.jsx](src/App.jsx): public `/`, `/marketplace`, `/item/:id`, `/u/:username` (seller page), `/privacy`, `/terms`, `/login`, `/signup` (the last two render `pages/Auth.jsx` with a `mode` prop); wrapped in `RequireAuth`: `/post`, `/profile` (always the signed-in user's own page), `/item/:id/edit`, `/messages`, `/messages/new/:listingId`, `/messages/:id`. A persistent `Navbar` sits above the routes. Provider order matters: `AuthProvider` outermost, then `ListingsProvider` and `MessagesProvider`, both of which read the current user. `vite.config.js` sets `historyApiFallback: true` so client-side routes work on refresh in dev.
- **Listings state**: [src/context/listings-context.js](src/context/listings-context.js) defines `ListingsContext` and `useListings()` (`{ listings, loading, error, addListing, updateListing, deleteListing }`); [src/context/ListingsContext.jsx](src/context/ListingsContext.jsx) holds the `ListingsProvider`. Context hooks and providers are split into separate files throughout (also `auth-context.js` / `AuthContext.jsx`) only because `react-refresh/only-export-components` forbids exporting a component and a hook from one file. The provider fetches the whole `listings` table once on mount (newest id first) — pages read from that in-memory array, so `ItemDetail` looks items up locally rather than querying by id, and a direct load of `/item/:id` must wait on `loading`. `addListing({ photos, ...fields })` and `updateListing(listing, { photos, ...fields })` take the form's complete, ordered photo list — items are `{ url }` (already stored) or `{ file }` (to upload) — and `resolvePhotos` uploads the new ones in parallel under `<user id>/` in the public `listing-images` bucket; if any upload fails the ones that succeeded are deleted again and the error is thrown. Both write `image_urls` (first = cover). After a successful update, photos that were on the listing but aren't in the new list are deleted from storage; a failed insert/update deletes the just-uploaded files; `deleteListing` deletes all of a listing's files (all best-effort via `removeStoredImages`). `updateListing` and `deleteListing` treat an empty result as "not yours" (RLS filters silently rather than erroring). The Supabase client is in [src/lib/supabaseClient.js](src/lib/supabaseClient.js), which throws at import if the env vars are missing.
- **Data shape**: a `listings` row has `id` (identity, higher = newer — `Marketplace`'s "Newest" sort relies on this), `title`, `price`, `category[]`, `seller`, `user_id`, `location` (display label), `latitude`, `longitude` (both null or both set), `condition`, `description`, `story`, `image_urls` (ordered text[], first = cover, max 5), `created_at`. `photos.sql` replaced the old single `image_url` column and adds a trigger requiring every photo URL to match, in full, `https://<something>.supabase.co/storage/v1/object/public/listing-images/<owner id>/<filename>` — anchored at both ends, because a substring check let a seller smuggle the owner's path into a query string of an arbitrary URL and use the image as a tracking pixel. The project's exact host can't be known inside SQL, so the built site's CSP (below) closes the remaining gap of another Supabase project's host. The category taxonomy (`categories`: Furniture, Fashion, Decor, Garden, Textiles, Lighting, Art, Tech, Tools, Cars) and badge colors (`tagColors`) are static in [src/data/categories.js](src/data/categories.js); categories are stored as plain text, not a table, so adding one is a code change only. Seed rows have `user_id` null, so no one can edit or delete them.
- **Marketplace filtering** ([src/pages/Marketplace.jsx](src/pages/Marketplace.jsx)) is done client-side in-component: search/category/sort state filters `useListings().listings` directly — there's no separate derived-state hook. The category control is [src/components/CategoryFilter.jsx](src/components/CategoryFilter.jsx): "All" plus the 5 categories with the most listings as pills (popularity = listing count, ties broken by taxonomy order in `data/categories.js`; computed from the loaded listings, so until they load only "All" and "More" show, to avoid pills visibly reshuffling), and a "More" panel listing every category with its count. Selection is single-choice; a category picked from "More" that isn't a pill appears as an extra highlighted pill with a ✕ that clears it. Adding a category to `data/categories.js` needs no change here.
- **Listing form**: [src/components/ListingForm.jsx](src/components/ListingForm.jsx) is the single form used by both `PostItem` and `EditItem` (validation, photo grid, error display). Pass `listing` to pre-fill it for editing; `onSubmit({ fields, photos })` does the saving and may throw to show an error. On success it deliberately stays in its submitting state because the caller swaps the screen or navigates away. Photos: up to 5, chosen several at a time; each passes through `prepareImage`, files that can't be used are skipped and reported together, the first photo is the "Cover" and any other can be made the cover, each has a ✕ to remove it; new photos show a blob-URL preview (tracked in a ref Set and revoked on removal/unmount). [src/pages/PostItem.jsx](src/pages/PostItem.jsx) shows a success screen with a "View Listing" link; [src/pages/EditItem.jsx](src/pages/EditItem.jsx) checks `listing.user_id === user.id` for a friendly message (the database enforces it regardless) and returns to the listing after saving. Neither sends `seller` or `user_id` — see Auth.
- **Design language** (pitfall: never add an unlayered global reset such as `* { margin: 0; padding: 0 }` to `src/index.css` — Tailwind v4 puts its utilities in a cascade layer and unlayered CSS always beats layered CSS, so it silently disables every `p-*`/`m-*`/`mx-auto` class; Tailwind's own preflight already does the reset. `src/App.css` is unused Vite-template leftover and isn't imported): no Tailwind config — colors are hardcoded hex values inline via arbitrary-value classes (e.g. `bg-[#1b4332]`, `text-[#52b788]`) rather than theme tokens. The palette is forest green / cream, with `'Fraunces'` (serif, Google Fonts, loaded in [index.html](index.html)) for headings and `'Inter'` for body text, both applied via inline `style={{ fontFamily }}` rather than Tailwind font classes. Keep new UI consistent with these same literal color values and font-family pattern unless doing a deliberate design pass.
- **Listing images**: [src/components/ListingImage.jsx](src/components/ListingImage.jsx) renders a listing's cover (`image_urls[0]`) or, if none, [ImagePlaceholder](src/components/ImagePlaceholder.jsx) (deterministic gradient + initials keyed off `id`); it takes a `className` for sizing and is used by `ListingCard` (which also shows a photo-count badge when there are several) and `NewMessage`. [src/components/PhotoGallery.jsx](src/components/PhotoGallery.jsx) is the listing page's main image (shown whole, `object-contain`) with previous/next buttons, a counter, and a thumbnail strip.
- **Auth & security model**: [src/context/AuthContext.jsx](src/context/AuthContext.jsx) wraps Supabase Auth (`user`, `username`, `loading`, `signUp`, `signIn`, `signOut`); the username is read from the `profiles` table (created by a trigger on `auth.users` from signup metadata, or a generated `user_xxxxxxxx` name for users made in the Supabase dashboard) so the UI always matches what the database stamps on listings. Usernames are lowercase `[a-z0-9_]{3,20}` so uniqueness is a plain equality check. Ownership is enforced in the database, not the client: a `BEFORE INSERT` trigger on `listings` overwrites `user_id` (from `auth.uid()`) and `seller` (from the profile), and a `BEFORE UPDATE` trigger (`editing.sql`) locks `id`, `user_id`, `seller` and `created_at`, so a client can't post as someone else or reassign a listing. RLS: anyone can read listings/profiles/images; only signed-in users can insert their own listings; only owners can update/delete them; storage writes are limited to the uploader's own folder. Reading is public, so the anon key in the frontend is safe — never use the `service_role` key here.
- **Messaging**: in-app buyer↔seller chat, no emails exposed. Tables `conversations` (one per buyer per listing; survives listing deletion with `listing_id` nulled and a `listing_title` snapshot) and `messages` in [supabase/messaging.sql](supabase/messaging.sql). Clients can't create conversations directly — there is no insert policy — only via the `start_conversation(listing_id, body)` RPC, which enforces: signed in, 1–2000 chars, listing exists, listing has an owner (seed/demo listings have `user_id` null and can't be messaged), and you're not the owner. Messages can be inserted by participants as themselves but never edited; read state changes only through the `mark_conversation_read` RPC; a trigger keeps `last_message`/`last_message_at` current for the inbox. Client queries live in [src/lib/messages.js](src/lib/messages.js). `MessagesProvider` exposes the navbar unread count and `refreshUnread()`; live updates use Supabase Realtime `postgres_changes` on `messages` (needs the table in the `supabase_realtime` publication, which messaging.sql adds; RLS still filters what each user receives). `Conversation.jsx` merges messages by id because a sent message can arrive both from the insert response and the realtime feed, and is keyed by conversation id so thread state resets between threads. `NewMessage.jsx` redirects to an existing thread if one exists; the conversation row is only created when the first message is sent.
- **Locations & distance**: a listing's `location` is a human-readable label and `latitude`/`longitude` are the position (a check constraint requires both or neither). Sellers choose a place from search suggestions in [src/components/LocationPicker.jsx](src/components/LocationPicker.jsx), so coordinates are a city centre, never a street address; free text without a suggestion is still saved as a label with null coordinates (legacy listings look like this) and simply has no distance. Place search is in [src/lib/geocode.js](src/lib/geocode.js) using Open-Meteo's free geocoding API (no key; free for non-commercial use only — swap that one module for another provider if that changes); `searchPlaces` also does ZIP codes. The *visitor's* location is separate: `LocationProvider` keeps `{ label, latitude, longitude }` in `localStorage` (`cycleup:location`) only — never sent to the server — and exposes `distanceTo(listing)` (miles via haversine in [src/lib/distance.js](src/lib/distance.js); `formatDistance` shows km outside US/UK locales). `getCurrentPlace()` (browser geolocation) rounds to 2 decimals (~1 km). `Marketplace` adds a "Distance: Nearest" sort only while a location is set (falls back to Newest if cleared; listings without coordinates sort last) and computes everything client-side over the already-fetched listings — fine at this scale; move to PostGIS if the catalog gets large. `LocationPicker`'s `value` prop is only its initial value (it owns its text afterwards).
- **Profiles**: [src/pages/Profile.jsx](src/pages/Profile.jsx) exports `MyProfile` (`/profile`, looked up by user id) and `UserProfile` (`/u/:username`, looked up by lowercased username), both rendering one `ProfileView`. It filters the already-loaded listings by `user_id === profile.id` (no extra query) and shows Edit/Delete/"New listing" plus the account email only when `user.id === profile.id`, so visiting your own `/u/<you>` gets the same owner controls as `/profile`. Profiles are public (username + join date; RLS already allows reading `profiles`), so no SQL was needed. `/profile` deliberately looks up by id rather than redirecting to `/u/<username>`, because `AuthContext.username` can briefly be a fallback (metadata or email) before the profile row loads. Seller names on cards and listing pages link to `/u/<seller>` only when the listing has a `user_id`; demo listings (null `user_id`, invented seller names) stay plain text since no such profile exists.
- **Marketing copy must be true**: the site is public, so never add invented statistics, testimonials, reviews, or claims about features that don't exist (there is no payment system, so nothing about commissions, payouts or "proceeds"; there are only a handful of real listings, so nothing about counts of items, sellers or users). The landing page's "How it works" and "Who it's for" sections deliberately describe only real features. If real numbers are wanted later, compute them live from the database rather than typing them in. The 9 seed listings (null `user_id`, invented sellers) are shown with a "Sample listing" badge on cards and pages and can't be messaged.
- **Legal pages & site facts**: [src/pages/Privacy.jsx](src/pages/Privacy.jsx) and [src/pages/Terms.jsx](src/pages/Terms.jsx) describe what the app *actually* does, so they must be updated (and `SITE.legalUpdated` bumped) whenever behaviour changes: adding analytics or any third-party service (also update the CSP in `public/_headers`), starting to collect new data, adding payments (the Terms currently say the site handles none), or changing retention/deletion. The published facts (operator name, contact email, governing law, last-updated date) live in [src/config/site.js](src/config/site.js). Shared layout pieces are in [src/components/LegalPage.jsx](src/components/LegalPage.jsx). The sitewide `Footer` (Privacy / Terms / Contact) is rendered by `App`, and the sign-up form links to both pages. These texts are a reasonable template, not legal advice.
- **Photo privacy**: [src/lib/image.js](src/lib/image.js) `prepareImage` re-encodes every uploaded photo through a canvas (JPEG, max 1600 px), which removes hidden metadata such as the GPS position phone cameras embed, applies EXIF rotation, and shrinks files. `ListingForm` refuses a photo the browser can't decode rather than uploading it untouched. The Privacy Policy promises this. Photos uploaded before this existed were not stripped.
- **Deleting a user** (privacy requests go to the contact email): Supabase dashboard → Authentication → Users → delete the user. After [supabase/deletion.sql](supabase/deletion.sql), that cascades to their profile, listings, and every conversation/message they're in (which also removes those conversations for the other person). It does **not** remove their photos: also delete the folder named with their user id under Storage → listing-images.
